# tanstack-todo - журнал решений

Действующие продуктовые, функциональные и архитектурные решения, включая процесс разработки: что решили, чем заплатили, что отвергли. Общая картина - в `DOCUMENTATION.md`, реализация - в коде.

## Как вести

- Пишем решение с реальными альтернативами, которое будущая задача может захотеть пересмотреть. Мелочь не пишем.
- Новая запись - в конец, со следующим номером. Номера не перенумеровываем: на них ссылаются.
- Если новое решение заменило часть старого, удаляем устаревшую часть. Полностью заменённую запись удаляем целиком. В новой записи упоминаем прежний вариант в «Отвергли», если причина отказа важна.
- Запись: заголовок «№. дата · что решили (#задача)», затем суть решения, «Цена», «Отвергли» - коротко, без деталей реализации. Пустой блок опускаем.

## 1. 2026-09-18 · Серверное состояние в TanStack Query, не в сторе

Данные приложения - серверное состояние в кэше TanStack Query: кэш, оптимистичные правки и инвалидация из коробки.
Отвергли: zustand - клиентский стор для серверных данных требует ручной синхронизации и расходится с сервером.

## 2. 2026-09-18 · Чтение: префетч в лоадере, компонент читает кэш

Лоадер роута заранее кладёт данные в кэш Query, компонент читает их через suspense-запрос. Единственный источник - кэш.

## 6. 2026-09-18 · Ошибки и «не найдено» - разные каналы

Сбои чтения показываем на экране ошибки роута с Retry. Для «не найдено» используем отдельный канал роутера. Правило отказа в доступе к доске описано в №83.

## 8. 2026-09-18 · Auth на Better Auth, не руками

Email + пароль на Better Auth, серверные сессии в HttpOnly-куке с SameSite=Lax. Подтверждение email выключено.
Отвергли: своя реализация - выше шанс ошибиться в криптографии, куках и CSRF.

## 9. 2026-09-18 · Проверка пользователя - серверная функция, не обычная

Проверка пользователя на сервере оформлена серверной функцией - на клиенте от неё остаётся только вызов по сети.
Отвергли: обычная экспортируемая функция - при импорте в клиентский код тащит Better Auth в клиентский бандл, и он падает (`Buffer is not defined`).

## 11. 2026-09-18 · Серверные функции - в `server/`, не в компонентах

Серверные функции вынесены из компонентов и роутов в `server/`, по файлу на домен - явная граница сервер/клиент, серверный код не утекает в клиент.
Цена: новый модуль серверных функций на лету ломает HMR - нужен рестарт dev-сервера.

## 12. 2026-09-18 · Кэш сессии в куке

Сессия кэшируется в куке, чтобы реже читать БД при каждой проверке сессии.

## 13. 2026-09-18 · Валидация форм - поле при уходе с него и при отправке

Каждое поле валидируется при уходе с него и при отправке формы. Клик по ссылке внутри формы не должен срываться из-за ухода с поля.
Отвергли: валидация на каждый ввод - ошибка с первого символа; валидация всей формы при уходе с поля - уход с одного поля подсвечивает все.

## 14. 2026-09-18 · Стратегия тестов - «трофей»

Много unit и компонентных тестов без базы, с замоканным сервером; меньше integration на изоляцию данных на настоящей базе - мок не проверит корректность SQL; мало e2e на Playwright.
Отвергли: Testcontainers для тестовой базы - сложнее отдельной локальной базы.

## 15. 2026-09-18 · SQL в репозиториях

SQL вынесен в репозитории `server/*-repo.ts`, чтобы integration-тесты могли проверять запросы к настоящей БД отдельно от вызова серверных функций.
Отвергли: мок базы скрывает ошибки SQL.

## 16. 2026-09-18 · Integration-тесты на отдельной базе

Два проекта Vitest - unit (jsdom, сервер замокан) и integration (node, настоящая база); integration отличаются суффиксом файла. Integration работают на отдельной тестовой базе и чистят её перед каждым тестом; сиды - прямой вставкой, не через тестируемый код.
Цена: тестовую базу нельзя путать с рабочей - очистка сотрёт данные.
Отвергли: тесты на dev-базе - очистка затрёт рабочие данные; отдельный контейнер под тесты - хватает второй базы в том же инстансе.

## 17. 2026-09-19 · Форматирование и линт перед коммитом

Перед коммитом хук форматирует и проверяет изменённые файлы. Полные проверки выполняет CI.

## 18. 2026-09-19 · Прод на Vercel + Neon, serverless

Прод на Vercel и Neon - бесплатно, отзывчиво, плюс serverless в портфолио.
Цена: нужен serverless-совместимый доступ к базе.
Отвергли: Railway - нет бесплатного тарифа; Render free - засыпает при простое, холодный старт 30-60 с, база временная.

## 20. 2026-09-19 · Без лимитера в памяти на serverless

Лимитер в памяти процесса убран; лимит частоты на мутации не ставим, пока нет нужды.
Отвергли: лимитер мутаций в памяти процесса. Его состояние сбрасывается при перезапуске и не разделяется между serverless-инстансами.

## 21. 2026-09-19 · Схема меняется версионированными миграциями

Изменения схемы - SQL-миграции, сгенерированные из схемы и закоммиченные; ими накатываются все базы, включая локальные. Синхронизация без истории (`push`) - только для быстрых локальных правок.
Цена: база, собранная через `push`, не принимает миграции - её нужно пересоздать.
Отвергли: `push` для прода - сравнивает схему с живой базой и может удалить или переписать данные без истории и ревью.

## 24. 2026-09-19 · На Neon приложение - через пулер, миграции - напрямую

На Neon приложение подключается через пулер, миграции - прямым подключением.
Отвергли: миграции через пулер - спотыкаются о его транзакционный режим.

## 26. 2026-09-19 · Тесты в CI - на временной Neon-ветке на прогон

Integration и e2e в CI создают свою Neon-ветку от прод-схемы, гоняют тесты и удаляют ветку при любом исходе. Прогоны не делят одну базу, а код проверяется на том же Neon, что и прод.
Цена: зависимость от Neon API и лимита веток - поэтому удаление обязательно.
Отвергли: одна статичная тестовая ветка для CI (было в №25) - параллельные прогоны пересекаются при очистке.

## 27. 2026-09-19 · Миграции прода - шагом CI после зелёных проверок

На push в `master` после зелёных quality, unit, integration и e2e CI накатывает миграции на прод; без новых миграций шаг ничего не делает. Vercel деплоит параллельно, поэтому миграции обратно совместимы, а разрушительные делятся на два релиза.
Отвергли: деплой внутри Actions после миграций - лишняя работа для нашего масштаба.

## 28. 2026-09-23 · E2E на Playwright

E2e - Playwright, только Chromium, последовательно: тесты делят одну тестовую базу. Сервер поднимается на `127.0.0.1` - на Windows `localhost` резолвится в `::1`, и готовность не ловится. Хелперы ждут гидрации перед действиями - иначе клик уходит нативной отправкой формы.

## 29. 2026-09-23 · Формы отправляются POST'ом

У форм `method="post"`: до гидрации нативная отправка кладёт поля в тело, пароль не попадает в URL, логи и историю.
Отвергли: полноценный progressive enhancement с серверным action без JS - избыточно для учебного проекта.

## 30. 2026-09-23 · E2E: логин один раз через setup-проект

Отдельный setup-проект один раз чистит базу, регистрирует пользователя и сохраняет сессию; рабочие сценарии переиспользуют её и между тестами чистят только данные досок, не пользователей. Сценарии самого входа идут без сохранённой сессии и без сброса базы - их изолируют уникальные email и скоуп по владельцу.
Отвергли: регистрация в каждом тесте - основная трата времени e2e; один длинный сценарий - падение маскирует, какой шаг сломался.

## 32. 2026-09-24 · Sentry без трейсинга, replay и feedback

Трейсинг, replay и feedback отключены ради приватности и квоты. Для отправки событий требуется DSN. Из событий исключаем тела запросов, куки, заголовки, данные запросов к базе и переменные стека, чтобы не передавать пароли и токены сессии.
Отложено: привязка ошибок к пользователю.

## 34. 2026-09-25 · CSRF-middleware на серверных функциях

Глобальный middleware отбивает cross-site вызовы серверных функций - второй слой поверх SameSite-куки, не зависящий от браузера и настроек кук. Sentry-middleware стоит первым, чтобы оборачивать и CSRF-отказы.
Отвергли: выключить предупреждение TanStack Start и полагаться на одну куку - защита дешёвая, причин отказываться нет.

## 36. 2026-09-25 · Доверенные хосты Better Auth - явным списком

Базовый URL Better Auth берётся из хоста запроса, если хост в списке: прод - всегда, превью-адреса проекта - только на превью, localhost - только вне Vercel. Протокол задан явно.
Отвергли: статичный URL прода - «Invalid origin» на превью и редиректы на прод; любой `*.vercel.app` - доверие любому деплою Vercel; маска превью на проде - даёт доверенный редирект после логина на чужой сайт; только доверенные origin - не чинит ссылки и редиректы на прод; URL из переменной деплоя - у деплоя два адреса, подхватится один.

## 38. 2026-09-25 · Vercel Web Analytics + Speed Insights

Просмотры и Core Web Vitals с реальных визитов - встроенные Vercel Analytics и Speed Insights. Перед отправкой id в адресах заменяются шаблоном: отчёт группируется, id не уходят в Vercel. Без cookies - баннер не нужен.
Цена: кастомные события только на платном плане; при малом трафике перцентили шумные.
Отвергли: PostHog, Plausible - для пета встроенного хватает.

## 42. 2026-09-25 · Спека на основной сессии, реализация - отдельный агент

Основная сессия прорабатывает задачу до точной спеки, реализацию делает отдельный агент implementer с узким контекстом: одна задача за запуск, точечное чтение. Главная экономия - от точной спеки и короткого контекста, а не от цены модели.
Отвергли: одна фоновая сессия на несколько задач - растущий контекст, разведка кодовой базы с нуля и сильная модель на механической работе обходятся дорого.

## 44. 2026-09-28 · `CODING.md` - уроки ревью и антипаттерны

Замечания ревью, которые могут повториться, становятся правилами в `CODING.md`; implementer читает его перед кодом. Только правила, где наш выбор отличается от поведения модели по умолчанию, в формате «правило - почему».
Отвергли: общие практики - по исследованию ETH Zurich файлы контекста не повышают успешность задач и удорожают прогон на 20%+; правила ESLint - пока не делаем.

## 45. 2026-09-28 · Миграции на временных CI-ветках перед тестами (#30)

На временные Neon-ветки из №26 применяются миграции проверяемой ревизии перед запуском тестов.

## 46. 2026-09-28 · Переход с todo на доски - через expand/contract (#31, #37, #44)

Смена модели данных шла в три шага: новая схема и идемпотентный перенос старых данных, пока старый интерфейс работает; затем переключение интерфейса и удаление старого кода; затем удаление старой таблицы и временной связи.
Цена: последний шаг необратим - данные, не перенесённые до него, потеряны.

## 47. 2026-09-28 · Миграции на превью - при сборке

Превью применяет миграции к своей базе перед сборкой приложения. Ошибка миграции останавливает сборку.

## 49. 2026-09-28 · Типы доски - из ответа сервера, удаление колонки - по наполнению (#35)

Типы доски, колонки и карточки не описываются отдельно, а выводятся из ответа серверной функции - одна точка истины с сервером. Пустая колонка удаляется сразу с Undo, непустая - через подтверждение без Undo: второй слой избыточен.
Отвергли: отдельные типы доски - риск разойтись с сервером.

## 50. 2026-09-28 · Доска, колонки и карточки загружаются вместе

Репозиторий загружает доску, колонки и карточки одним запросом. При SSR доска сразу в HTML. Если загрузка замедлится, сначала рассматриваем пагинацию карточек в колонке, затем потоковый SSR.
Отвергли: колонки, затем карточки по колонкам параллельно - минимум два последовательных round-trip и N вызовов без выигрыша во времени.

## 52. 2026-09-29 · Краевые случаи в спеке, «проверено» - только тестом

В спеке раздел краевых случаев (3-5 сценариев, у каждого - «тест» или «превью»). Агент считает проверенным только то, что доказал тест или CI, остальное помечает «не проверено». Тело PR - на русском, заголовок - на английском, он становится коммитом.
Отвергли: общие чеклисты и таблицы самопроверки - создают видимость проверки и подгонку под список.

## 54. 2026-09-29 · `/` ведёт на список досок, доски по умолчанию нет (#46)

`/` редиректит на `/boards`. Пользователь с новой обычной учётной записью видит пустой список и сам создаёт доску без колонок.
Отвергли: доска по умолчанию, создаваемая лениво при первом входе (было в №48) - как в Trello, пользователь создаёт доску сам; колонки по умолчанию у новой доски - были нужны только для переноса todo.

## 55. 2026-09-30 · Мягкое удаление колонок и карточек (#49)

Удаление колонки или карточки сразу помечает её удалённой. Восстановление выполняется отдельной операцией. Карточки удалённой колонки скрываются вместе с ней и сохраняют своё состояние. Условия показа Undo для колонок описаны в №49. Доски удаляются навсегда.
Цена: удалённое копится, очистка по расписанию отложена до реальной необходимости.
Отвергли: блокировать перечитывание на время окна Undo - хрупко и не спасает при уходе со страницы; удаление насовсем (было №4) - без истории нет Undo; отложенный DELETE с Undo-тостом (было №5) - кэш и сервер расходятся на всё окно Undo.

## 56. 2026-09-30 · Создание без оптимизма - в кэше только то, что есть на сервере (#59)

Создание доски, колонки и карточки ждёт ответ сервера с настоящей записью; пока запрос идёт, поле сохраняет фокус и показывает спиннер, при ошибке текст остаётся. Переименование, перенос и удаление остаются оптимистичными - они работают с настоящими id.
Отвергли: оптимистичное создание с временным id (было в №49) - поддельная сущность требовала проверок и блокировок, при замене id закрывались меню, ссылка вела на несуществующую карточку; «призрак» из состояния мутации - тот же поддельный элемент, только вне кэша; id от клиента - доверие к id клиента и обработка конфликтов ради одного round-trip.

## 57. 2026-10-02 · Общая превью-база для всех PR

Все превью используют общую Neon-ветку `staging`.
Цена: один PR с миграцией за раз; если PR с миграцией закрыт без мержа или миграцию перегенерировали - ручной сброс `staging` и redeploy превью, после сброса в ней копия прод-данных.
Отвергли: Neon-ветка на каждое превью с удалением при закрытии PR (было №37, №43) - упиралось в лимит веток Neon; ветка только для PR с миграциями, авто-сброс `staging`, защита от дрейфа миграций - лишняя сложность при одном разработчике.

## 58. 2026-10-02 · Порядок карточек - строковый ключ, считает сервер (#81)

Позиция - строковый ключ с побайтовой сортировкой; перемещение меняет одну строку, колонку не перенумеровываем. Клиент присылает соседей, сервер проверяет их и считает ключ; при гонке двух вкладок ключи перенумеровываются.
Отвергли: целые позиции с перенумерацией колонки - много записей на каждый перенос; ключ от клиента - доверие к данным клиента и конфликты.

## 59. 2026-10-02 · DnD на стабильном `@dnd-kit/core`, не на `@dnd-kit/react` (#81)

Перетаскивание на `@dnd-kit/core` + `sortable`: мышь, тач, клавиатура, автопрокрутка и озвучка для скринридера - из коробки. Своё - определение цели броска по колонке и стрелки между колонками.
Цена: у `@dnd-kit/core` нет релизов с 12.2024 - риск принят; с React 19 работает, проверено e2e.
Отвергли: `@dnd-kit/react` - версия 0.x, API меняется.

## 60. 2026-10-02 · Перемещения - очередь мутаций и перечитывание вместо отката (#81)

Создание и перемещения на доске идут одной очередью - сервер считает ключ по уже сохранённым позициям предыдущих запросов. При ошибке - тост и перечитывание доски; после успеха перечитываем, только когда очередь пуста. Пока у карточки есть перемещение в очереди, её удаление недоступно.
Отвергли: откат снимка при ошибке - поверх него уже лежат следующие перемещения очереди; перечитывание после каждого успеха - ответ без ещё не сохранённых перемещений вернул бы карточки назад.

## 63. 2026-10-05 · Лимитер auth в Postgres, квоты на содержимое (#83)

Счётчики лимитера Better Auth хранятся в базе - общие для всех serverless-инстансов. Лимиты на вход и регистрацию строже общих; запрос без определимого IP попадает в общий счётчик, а не пропускается. Квоты на число досок, колонок и карточек проверяются при вставке, восстановлении и переносе карточки - иначе лимит обходится циклом «удалить - создать - Undo».
Цена: подсчёт и запись выполняются отдельно, поэтому параллельные операции могут превысить квоту.
Отвергли: Upstash Redis или отдельное хранилище - лишний сервис ради одной таблицы; CAPTCHA и Vercel Firewall - вне скоупа; встроенный лимитер Better Auth без хранилища - счётчики в памяти инстанса на Vercel почти не ограничивают.

## 64. 2026-10-06 · Отключение лимитера auth через окружение (#106)

Лимитер включён по умолчанию. `AUTH_RATE_LIMIT_DISABLED=true` отключает его. При отключении на превью переменная задаётся в настройках Vercel за пределами репозитория.
Цена: в окружении с отключённым лимитером его нельзя проверить вручную. Лимитер покрывают integration-тесты.
Отвергли: условие на превью в коде - включить лимитер на превью можно только коммитом; поднять лимиты на превью - правила расходятся с продом; постоянные тестовые пользователи - общее состояние между прогонами и дополнительные секреты.

## 66. 2026-10-06 · Гость - отдельный пользователь с демо-доской (#84)

Гость получает отдельную анонимную учётную запись Better Auth со своей демо-доской. Просроченные гостевые аккаунты удаляются при создании нового гостя, а общее число гостей ограничено. Сервер выбирает меньшие квоты для гостя по сессии. При регистрации гостевая учётная запись и её данные удаляются. Доступ по приглашению описан в №85.
Цена: зарегистрировавшись, гость теряет свою доску.
Отвергли: read-only демо или общий демо-аккаунт - урезанный функционал или общие данные гостей; удаление гостей по расписанию - нужна отдельная инфраструктура; перенос данных при регистрации - сложнее из-за слияния досок и квот, для портфолио не нужен.

## 68. 2026-10-08 · Порядок колонок - как у карточек, перенос между досками - через Move (#97)

Колонки упорядочены так же, как карточки (№58). Перетаскивание колонок - в общем DnD-контексте с карточками и в общей очереди мутаций доски. На другую доску колонку переносят только через окно Move.
Отвергли: отдельный DnD-контекст для колонок - вложенные контексты не делят сенсоры и очередь, а запросы колонок и карточек должны идти по порядку; перенос между досками перетаскиванием - между досками нет общего экрана.

## 71. 2026-10-12 · Срок карточки - дата или момент, двумя полями (#120)

Срок «на весь день» хранится датой без таймзоны, срок со временем - точным моментом; база разрешает не больше одного. День сравнивается с локальной датой устройства, момент - с текущим временем.
Отвергли: один момент с флагом «весь день» - полночь в одной таймзоне в другой съезжает на соседний день; текстовое поле - теряются типы и сравнения в базе.

## 72. 2026-10-12 · Метки принадлежат доске (#120)

У каждой доски свой набор меток, на карточку вешается только метка её доски. При переносе колонки на другую доску метки её карточек снимаются, форма переноса заранее предупреждает; срок, выполнение и чек-лист сохраняются.
Цена: снятие меток - отдельный запрос без транзакции; при его сбое на новой доске остаются связи со старыми метками, клиент их не показывает.
Отвергли: метки пользователя, общие для всех досок - лишний экран управления и неочевидная область видимости; сопоставление меток по названию и цвету при переносе - неоднозначно из-за дублей и меток без названия.

## 73. 2026-10-12 · Прогресс чек-листа - вместе с доской, пункты - отдельно (#120)

Карточке на доске нужен только счётчик «сделано из всего», он считается в том же запросе доски. Пункты грузятся отдельно, когда открывается окно карточки.
Отвергли: счётчики, хранимые в карточке - без транзакций их пришлось бы синхронизировать вторым запросом на каждую правку, расхождения не чинятся сами; пункты вместе с доской - раздувают каждый запрос доски ради окна одной карточки.

## 74. 2026-10-12 · Даты на сервере - по таймзоне устройства из cookie (#120)

Клиент сохраняет таймзону устройства в cookie, сервер рендерит относительные даты по ней и по времени запроса, после гидрации клиент переключается на устройство.
Цена: на первом визите cookie нет - сервер рендерит в UTC, даты перерисовываются после гидрации.
Отвергли: даты только на клиенте - пустые места или мигание на каждой загрузке; всегда UTC на сервере - неверный «Today» у всех вне UTC до гидрации; таймзона в профиле - нужна настройка, а у гостя и нового устройства её нет.

## 75. 2026-10-12 · Одна очередь мутаций на карточку (#120)

Все правки содержимого карточки - выполнено, срок, метки, чек-лист - идут в одну очередь: быстрые клики доходят до сервера по порядку, данные перечитываются после последней правки. При ошибке - тост и перечитывание без отката.
Отвергли: независимые мутации - запросы обгоняют друг друга, перечитывание после первой затирает следующие оптимистичные правки; откат при ошибке - не учитывает правки, вставшие в очередь позже.

## 77. 2026-10-15 · Локально Docker Postgres, драйвер по хосту (#127)

Локально Postgres в Docker - база для разработки и база для тестов; CI, превью и прод - на Neon. Драйвер выбирается по хосту базы: локально node-postgres, на Neon - neon-http. Код использует только общее у обоих драйверов - без транзакций и batch.
Цена: локально не проверяется HTTP-транспорт Neon - это ловят integration и e2e в CI на Neon-ветках.
Отвергли: neon-http через прокси локально - медленно; node-postgres или neon-serverless на проде - отдельное решение с риском для serverless-соединений, вернуться, если понадобятся транзакции; PGlite - третий драйвер и не покрывает dev-сервер; драйвер по признаку Vercel - node-postgres локально и в CI (было №19); neon-http везде и тесты на Neon-ветке `test` (было №22, №23) - медленно и нестабильно через сеть.

## 78. 2026-10-19 · Всплывашка окна карточки отвязана от своей кнопки (#133)

Всплывашку рисует окно карточки отдельно от кнопок; она встаёт у кнопки в момент клика, кнопка только переключает её. Всплывашка не закрывается и не уезжает, когда кнопка переезжает между рядами, на десктопе и в мобильной шторке.
Цена: после закрытия фокус не возвращается на кнопку; при прокрутке окна всплывашка не едет за кнопкой.
Отвергли:

- одна общая всплывашка над рядами - не работает в мобильной шторке;
- переносить саму кнопку без пересоздания - слишком сложно;
- чинить только десктоп - мобильный остаётся сломан;
- замораживать окно, пока всплывашка открыта, - окно за ней перестаёт обновляться.

## 79. 2026-11-02 · Автоматический Verifier удалён из процесса и репозитория

После зелёного CI PR передаётся владельцу на приёмку. Workflow Verifier, окружение QA и скрипт ожидания удалены; инструкция агента сохранена как неактивная справка для переработки. Обязательный отчёт о прогоне отменён.
Цена: независимое ревью и QA не гарантированы процессом.
Отвергли: обязательный Verifier и отчёт о прогоне (было №41, №65, №67), автоматический запуск в GitHub Actions (было №61, №62) - процесс упрощён на время переработки Verifier.

## 80. 2026-11-03 · Переработка процесса разработки

Процесс разработки перерабатывается: подробный регламент в `CONTRIBUTING.md` сокращён, шаблоны issue и PR удалены. Сохраняем базовые конвенции и роли.
Цена: часть шагов временно определяется в конкретной задаче.
Отвергли: жёсткий пошаговый процесс с одноразовыми implementer, этапами проработки и цепочкой слайсов (было №69, №70, №76) - пересматриваем процесс целиком.

## 81. 2026-11-07 · Integration и e2e параллельно (#155)

Качество (lint и typecheck) и unit идут параллельно; после их успеха integration и e2e запускаются параллельно.
Цена: падение integration не отменяет уже запущенный e2e.
Отвергли: e2e после integration (было №31) — удлиняет CI при уже изолированных базах.

## 82. 2026-11-07 · Выборочные integration и e2e перед пушем (#153)

Добавляем к припуш новые и изменённые integration и e2e из diff текущего пуша.
Цена: нужен чистый рабочий каталог и пуш текущего HEAD одной ветки; тестовое окружение готовится заранее. Изменение только прикладного кода не запускает неизменённые integration и e2e до CI.
Отвергли: обязательный ручной прогон своих тестов (было №33) — забывается и удлиняет цикл обратной связи; поиск связанных тестов, хранение результатов прогонов и специальные проверки пропусков — вне минимальной задачи.

## 83. 2026-10-27 · Доступ к доске - шлюз по роли, карта прав, пропуск в репозиторий (#140)

Права живут только на уровне доски, всё внутри доски наследует их. Каждая серверная функция над доской сначала проходит шлюз: найти доску ресурса, роль пользователя на ней, разрешено ли роли действие по карте прав. Шлюз выдаёт пропуск, без которого репозиторий не вызвать: это проверяет компилятор. SQL репозитория дополнительно ограничивает строки досками, где пользователь владелец или участник, без учёта роли. Карта «действие → роли» одна для сервера и UI: UI по ней только скрывает элементы. Отказ это ошибка, а не пустой результат; 0 изменённых строк после шлюза тоже ошибка.
Цена: дополнительный запрос роли на каждую операцию; меняются сигнатуры всех репозиториев; приглашение проходит отдельным шлюзом по токену.
Отвергли:

- проверка только внутри каждого запроса (было №48) - правила ролей размазаны по десяткам запросов, отказ тихий;
- только шлюз без SQL-ограничения - забытый шлюз открывает чужие доски;
- двойная проверка без пропуска - при забытом шлюзе участник делает действие владельца;
- ранги ролей вместо явной карты - лестница не строгая (выход есть у всех, кроме владельца);
- права в таблице БД - избыточно для двух ролей;
- права на уровне колонок и карточек - не нужны, всё содержимое общее.

## 84. 2026-10-27 · Владелец - в `boards.owner_id`, участники - в отдельной таблице с ролью (#140)

Владелец остаётся полем доски, участники хранятся отдельно с ролью. Сейчас роль одна, `editor`: так при появлении viewer и admin данные не мигрируют. Роль владельца вычисляется из поля доски.
Цена: роль собирается из двух мест; правила «роль против роли» (admin против owner) не заложены.
Отвергли:

- владелец тоже в таблице участников - на поле доски держится каскадное удаление досок вместе с пользователем, в том числе очистка гостей; «ровно один владелец» пришлось бы обеспечивать отдельно; миграция всех досок;
- роль `member` - при появлении ролей пришлось бы мигрировать.

## 85. 2026-10-27 · Приглашение - многоразовая ссылка доски до сброса, только владельцу (#140)

У доски одна ссылка-приглашение; первый Share создаёт её и делает доску общей навсегда, сброс заменяет ссылку. Токен хранится открыто, чтобы владелец мог скопировать ссылку в любой момент. Вступление по ссылке, без писем и подтверждения владельцем. Гости вступают и делятся наравне со всеми.
Цена: утёкшая ссылка работает до сброса; удалённый участник может вернуться по текущей ссылке, владельцу советуем её сбросить; при удалении гостя пропадают и его общие доски.
Отвергли:

- добавление по email - человека можно добавить без согласия, нужен уже существующий аккаунт;
- одноразовые ссылки и отдельная таблица приглашений - одна ссылка на команду проще;
- хеш токена - ссылку нельзя показать повторно;
- срок жизни, лимит вступлений, запрос доступа, бан удалённых - вне минимума.

## 86. 2026-10-27 · Одновременные правки - последняя запись побеждает (#140)

На общей доске поле сохраняет последний записавший. Устаревшие переносы и правки удалённого сервер отклоняет, клиент показывает ошибку и перечитывает доску. Чужие изменения видны при перечитывании, без realtime и опроса по таймеру.
Цена: одновременная правка одного поля тихо затирает чужую; пока не перечитал, видишь старую доску.
Отвергли:

- проверка версии записи - версия в каждой мутации и обработка конфликта, очередь собственных правок конфликтует сама с собой;
- блокировка на время правки и слияние правок - нужен realtime.
