# Работа с репозиторием

Конвенции для задач, веток, коммитов и PR. Процесс: обсуждение → спека в issue → implementer → verifier → приёмка владельцем → squash-мерж (подробно - «Процесс фичи»).

- Язык: заголовок issue, ветки, коммиты и заголовок PR - на английском; тело issue (блоки Task-формы, поля Bug-формы) и тело PR - на русском. Доки (`DOCUMENTATION.md`, `DECISIONS.md`) - на русском.
- Сначала issue: черновик показываю владельцу, создаю после «ок». Шаблоны - `.github/ISSUE_TEMPLATE/` (Task, Bug); метки `feature`, `bug`, `chore`, `docs`, `refactor`.
- Ветка от свежего `master`: `type/<issue>-short-slug` (`feat/12-todo-owner-index`).
- Коммиты - Conventional Commits: `type(scope): summary` (feat, fix, refactor, test, docs, chore, perf, ci, build), повелительное наклонение, до ~72 символов. Сгенерированное (миграции, lock-файл) и механическое (переименования, форматирование) - отдельными коммитами. Порядок коммитов - для чтения: schema/migration → core → tests → docs.
- PR: заголовок в формате Conventional Commit (при squash становится коммитом в `master`), `Closes #N`, шаблон `.github/pull_request_template.md` заполнен целиком: ручные действия перед мержем - в «Before merging», карта чтения файлов - в «Review guide», риски - в «Look closely at».
- Мелкий PR (docs/chore/config, без логики, до ~50 строк) - сокращённое описание: `Closes`, «Before merging» (если есть), «Why», «What changed», «How to verify»; остальные разделы удаляются.
- Один PR - одна фича, без «заодно». Фича - законченная пользовательская возможность целиком (БД → UI), которую можно принять на превью; на несколько PR режем, только если её нельзя проверить по частям.
- PR открывается как draft. В «ready for review» его переводит основная сессия, когда verifier дал «ок», вместе с комментарием `[claude summary]` (см. ниже). Draft = ещё в цикле разработчик ↔ verifier.
- Inline-комментарии самоаннотации - только для нетривиальной логики, 3-5 штук одним ревью; иначе хватает «Review guide».
- Замечания ревью - новыми коммитами, без force-push во время ревью.
- Мержит только владелец (squash, ветка удаляется автоматически). Агент не мержит никогда.

## Процесс фичи

Фича = 1 issue = 1 PR, в работе одна фича за раз. Одна фича = одна сессия основной модели: состояние живёт в issue, PR и доках, а не в чате.

### Роли

| Роль                                                           | Отвечает за                                                                                                                                                                                            | Готово, когда                                    |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| Владелец                                                       | Продукт и ключевые тех-решения: одобряет спеку, принимает PR на превью, фидбэк - в чат, мержит                                                                                                         | Merge                                            |
| Основная сессия (техлид)                                       | Спека, запуск агентов, ожидание CI и verifier фоновыми скриптами, передача между агентами, арбитраж (споры, nit, застрявший агент), сводка владельцу. Код сама не пишет и diff целиком не перечитывает | Спека одобрена; PR дошёл до владельца со сводкой |
| `implementer` (разработчик, `.claude/agents/implementer.md`)   | Код, тесты на новую логику, прогон своих тестов, push, draft PR. Одноразовый запуск: на каждую починку - новый агент                                                                                   | Push сделан, отчёт основной сессии               |
| `verifier` (ревьюер + ручной QA, `.claude/agents/verifier.md`) | Соответствие спеке и `CODING.md`, нет лишнего, тесты не пустые, сценарии работают руками на превью. Код не пишет                                                                                       | Вердикт «ок» или список правок                   |

### Цикл

1. Обсуждение → спека в issue → «ок» владельца.
2. `implementer`: код, свои тесты, push, draft PR → завершается с финальным отчётом (PR, head SHA). CI не ждёт, метку `verify` не ставит.
3. Основная сессия запускает фоновой командой `scripts/wait-ci.sh <PR> <HEAD_SHA>` (последний прогон `ci.yml` `pull_request` по SHA, ≤40 мин). `0` (зелёный) → `gh pr edit <PR> --add-label verify` и шаг 4. `1` (красный) → выдержка из `gh run view <id> --log-failed` (только упавшее) → починка (ниже) → снова скрипт с новым SHA. `4` (cancelled: прогон вытеснен новым push) → скрипт по последнему SHA. Эскалация владельцу: красный после 2 починок CI, `3` (timeout).
4. `verifier` - workflow `verify.yml` в GitHub Actions, запускается меткой `verify`: ревью + ручной QA на превью Vercel → агент пишет `report.md` и `verdict.json` (токена GitHub у него нет) → workflow проверяет JSON, считает вердикт и публикует отчёт `[verifier]` комментарием в PR (JSON - скрытым блоком `<!-- verifier:json -->`). Прогон зелёный только при «ок»; «правки», некорректный или несформированный отчёт - красный. Есть прошлый отчёт - лёгкий режим (его правки, комментарии владельца после него, diff от проверенного коммита). Поставив метку, основная сессия запускает фоновой командой `scripts/wait-verify.sh <PR> <HEAD_SHA>` (ждёт завершения прогона `verify.yml` по SHA, ≤35 мин) и по комментарию `[verifier]` этого SHA действует сама: «ок» → шаг 5 и push владельцу; «правки» → blocker/should (без nit и ложных, их исход - в таблицу `[claude summary]`) → починка → шаг 3; «отчёт не сформирован» → один раз `gh run rerun <id> --failed` и снова скрипт. Эскалация владельцу (ссылка на прогон): «правки» после 2 раундов (раунд = комментарий `[verifier] правки` в PR), `timeout` скрипта, повторное «не сформирован», нет вердикта («CI не зелёный», «превью не готово», «отчёт некорректен», комментария по SHA нет).
5. Основная сессия: draft → ready, комментарий `[claude summary]`: решения, чувствительные места (ссылки на файлы), вердикт verifier, что не проверено; если дифф меняет `.github/workflows/verify.yml`, `.claude/agents/verifier.md`, `CODING.md` или `DECISIONS.md` - отдельной строкой «PR меняет правила verifier: …»; таблица «id замечания → исход (исправлено / отклонено как ложное / nit)» по всем раундам.
6. Читая фидбэк, основная сессия смотрит все комментарии PR, не только последний. Владелец: решения, превью, фидбэк в чат → основная сессия превращает его в список правок → починка → шаг 3 (метка `verify` → `verifier` в лёгком режиме).
7. Апрув владельца в чате сессии фичи → основная сессия публикует отчёт о прогоне `[run report]` по skill `.claude/skills/run-report` (до мержа: в этой сессии известны id агентов implementer). Merge - владелец.

**Починка** (красный CI, правки verifier или владельца) - всегда новый `implementer`, не SendMessage прежнему. Задание от основной сессии своими словами: спека (issue), PR, что сломано (выдержка лога CI, blocker/should из `[verifier]` или правки владельца). Агент чинит только это, пушит, завершается; замеченное вне задачи - в отчёт, не в код. Handoff-файлов и комментариев передачи в PR нет: хватает финального отчёта, описания PR, лога CI и `[verifier]`. Лимиты: ≤2 починки на CI, ≤2 раунда verifier, затем эскалация владельцу.

Ни один агент не держит контекст во время ожидания: CI и verifier ждут фоновые скрипты основной сессии. `implementer` работает в основном репо `D:/sandbox/claude/programming/tanstack-todo`, ветка от свежего `origin/master`; worktree не используем (одна фича за раз).

### Застрявший агент

Агент, который не может продолжить (вопрос, ошибка, сеть Neon), завершается с отчётом, а не ждёт. Основная сессия запускает нового с новой гипотезой; продуктовые вопросы - владельцу. После 2 неудачных гипотез - стоп, сводка владельцу и push-уведомление. Цикл живёт, пока открыта сессия: при долгой работе основная сессия включает keep-awake.

### Когда дёргаем владельца

Только в 3 точках, с push-уведомлением: спека готова к одобрению; эскалация; PR готов к приёмке.

### Формат спеки (issue)

Спека прорабатывается по этапам скилла `task-design` (`.claude/skills/task-design/SKILL.md`): брейншторм → product design → system design → code design → слайсы. Блоки issue - по шаблону Task: Context, Product design, System design, Code design, Slices. Перед спекой - `git fetch`, код читаем с `origin/master`, не с локальной ветки. Критерии приёмки - пронумерованные сценарии «делаю X → вижу Y»: по ним пишет тесты implementer, проверяет verifier, принимает владелец.

### Журнал исходов

Данные для оценки verifier - только в GitHub: JSON-вердикты в комментариях `[verifier]`, таблица исходов в `[claude summary]`. Данные о прогоне фичи (этапы, время, циклы, классы ошибок, токены, стоимость и промахи кэша implementer) - JSON в комментарии `[run report]`. Дефект, который verifier пропустил (найден владельцем или после мержа), - Bug-issue с меткой `escaped` и ссылкой на PR, где его не заметили.

### Проверки: кто что гоняет

- `implementer`: только свои новые/изменённые тесты (любого типа), для новой логики - red-green (тест сначала падает); для мелких багфиксов и вёрстки red-green не нужен; typecheck/lint/unit - хуки; полный набор - CI. CI не ждёт.
- CI - единственный источник истины «всё зелёное». Ждёт его основная сессия (`scripts/wait-ci.sh`), лог упавшего читает она же.
- `verifier` тесты не перезапускает; ручной QA - одноразовым Playwright-spec в `e2e/_verify/` (в git не попадает) через `playwright.verify.config.ts` против превью, по 2 новых юзера на прогон, только по критериям и краевым случаям спеки.
- Вывод тестов - компактный репортер (`--reporter=line`), в контекст - только упавшее. Замеры вместо скриншотов.

### Neon локально

Миграции на локальные ветки `e2e`/`test` катить можно, на `main` - никогда. Если предыдущая фича с миграцией не смержена или миграцию перегенерировали, перед новой фичей ветку `e2e` (и `test`, если трогали) сбрасывают от родителя (Neon Console → Reset from parent; локально API-ключа Neon нет - делает владелец по просьбе основной сессии).

## Правила кода

- `CODING.md` - уроки из код-ревью и антипаттерны. Замечание из ревью, которое может повториться, добавляется туда правилом в том же PR, где оно исправлено. Общие практики не добавляем.
