# Работа с репозиторием

Конвенции для задач, веток, коммитов и PR. Процесс: обсуждение → спека в issue → implementer → CI → приёмка владельцем → squash-мерж

- Язык: заголовок issue, ветки, коммиты и заголовок PR - на английском; тело issue (блоки Task-формы, поля Bug-формы) и тело PR - на русском
- Сначала issue: черновик показываю владельцу, создаю после «ок». Шаблоны - `.github/ISSUE_TEMPLATE/` (Task, Bug); метки `feature`, `bug`, `chore`, `docs`, `refactor`.
- Ветка от свежего `master`: `type/<issue>-short-slug` (`feat/12-todo-owner-index`).
- Коммиты - Conventional Commits: `type(scope): summary` (feat, fix, refactor, test, docs, chore, perf, ci, build), повелительное наклонение, до ~72 символов. Сгенерированное (миграции, lock-файл) и механическое (переименования, форматирование) - отдельными коммитами. Порядок коммитов - для чтения: schema/migration → core → tests → docs.
- PR: заголовок в формате Conventional Commit (при squash становится коммитом в `master`), `Closes #N`, шаблон `.github/pull_request_template.md` заполнен целиком
- Мелкий PR (docs/chore/config, без логики, до ~50 строк) - сокращённое описание: `Closes`, «Before merging» (если есть), «Why», «What changed», «How to verify»; остальные разделы удаляются.
- Один PR - одна фича, без «заодно». Фича - законченная пользовательская возможность целиком (БД → UI), которую можно принять на превью;
- PR открывается как draft. После зелёного CI основная сессия переводит его в «ready for review» вместе с комментарием `[claude summary]` (см. ниже). Draft = реализация и проверки ещё не завершены.
- Замечания ревью - новыми коммитами, без force-push во время ревью.
- Мержит только владелец (squash, ветка удаляется автоматически). Агент не мержит никогда.

## Процесс фичи

### Роли

**Владелец** отвечает за продукт и ключевые технические решения: одобряет спеку, принимает PR на превью, даёт фидбэк в чате и мержит. Работа завершена после мержа.

**Основная сессия (техлид)** готовит спеку, запускает агентов, ждёт CI фоновым скриптом, передаёт задачи между агентами, разбирает спорные вопросы и помогает застрявшим агентам. Код сама не пишет и diff целиком не перечитывает.

**`implementer` (разработчик, `Agents/implementer.md`)** пишет код и тесты на новую логику, прогоняет свои тесты, делает push и открывает draft PR. На каждую починку запускается новый агент. Завершает работу после push и отчёта основной сессии.

### Цикл

1. Обсуждение → спека в issue → «ок» владельца.
2. `implementer`: код, свои тесты, push, draft PR → завершается с финальным отчётом (PR, head SHA). CI не ждёт.
    - Крупная задача (блок Slices в issue) - цепочка `implementer` в одной ветке и одном PR, по агенту на слайс. До запуска основная сессия комментарием в issue раскладывает слайсы и привязывает каждый критерий приёмки к слайсу. Первый слайс создаёт ветку и draft PR; схема и миграция - только в нём, следующие `schema.ts`/`drizzle/` не трогают (не хватает - стоп и вопрос). Каждый слайс дописывает в описание PR раздел «Слайс N» и в отчёте передаёт следующему экспорты и места подключения; последний приводит описание к шаблону. Следующий слайс стартует сразу по отчёту: CI между слайсами не ждём. Старые тесты чинит слайс, который их сломал (unit/component - хук, integration/e2e своей области - точечный прогон перед push). После последнего слайса - шаг 3 один раз.
3. Основная сессия запускает фоновой командой `scripts/wait-ci.sh <PR> <HEAD_SHA>` (последний прогон `ci.yml` `pull_request` по SHA, ≤40 мин). `0` (зелёный) → шаг 4. `1` (красный) → выдержка из `gh run view <id> --log-failed` (только упавшее) → починка (ниже) → снова скрипт с новым SHA. `4` (cancelled: прогон вытеснен новым push) → скрипт по последнему SHA. Эскалация владельцу: красный после 2 починок CI, `3` (timeout).
4. Основная сессия: если в задаче принято решение с альтернативами - запись в `DECISIONS.md` коммитом в ветку PR; draft → ready, комментарий `[claude summary]`: решения, чувствительные места (ссылки на файлы), что не проверено.
5. Читая фидбэк, основная сессия смотрит все комментарии PR, не только последний. Владелец: решения, превью, фидбэк в чат → основная сессия превращает его в список правок → починка → шаг 3.
6. Апрув владельца в чате сессии фичи → merge владельцем.

`implementer` работает в основном репо `D:/sandbox/claude/programming/tanstack-todo`, ветка от свежего `origin/master`; worktree не используем

### Застрявший агент

Агент, который не может продолжить (вопрос, ошибка, сеть Neon), завершается с отчётом, а не ждёт. Основная сессия запускает нового с новой гипотезой; продуктовые вопросы - владельцу.
