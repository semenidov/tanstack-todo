# task-design

Идём по этапам, не перескакивая. Каждый этап заканчивается подтверждением владельца, после него результат записывается в свой блок issue (шаблон `.github/ISSUE_TEMPLATE/task.yml`). Issue создаётся после первого этапа: черновик → «ок» владельца → создание. Перед каждой правкой issue тело перечитывается с GitHub, чтобы не затереть правки владельца. Каждое решение записано в одном блоке, без повторов.

## 1. Брейншторм

- Список гипотез: что, зачем, польза пользователю, чем сложно.
- Прорабатываем решения, выбираем, какие фичи берём в задачу.
- В issue: **Context** - что делаем и зачем.

## 2. Product design

- Разбираем сценарии и UX, показываем макеты.
- Уточняем вопросы по функционалу, думаем, что ещё добавить.
- Конкретизируем продуктовые сценарии.
- В коде на этом этапе не копаемся, PR не предлагаем.
- В issue: **Product design** - поведение, примерные вайрфреймы, критерии приёмки «делаю X → вижу Y», out of scope.

## 3. System design

- Верхним уровнем: данные, хранение, чтение, запись, консистентность, доступ.
- Сложные кейсы, спорные сущности, масштаб, совместимость.
- Сначала сверяемся с `DECISIONS.md`, чтобы не переобсуждать решённое.
- В issue: **System design**.

## 4. Code design

- Карта файлов: что где лежит и за что отвечает. Не дальше интерфейсов.
- Структуру сверяем с `origin/master`.
- В issue: **Code design**.

## 5. Слайсы

- Одна задача - один PR.
- Сначала общая логика (схема, общая инфраструктура), затем функционал по фичам отдельными коммитами, от простого к сложному.
- В issue: **Slices** - план коммитов.

Для мелких задач (bug, chore) этапы 3-5 можно пропустить, если владелец не просит иного.
