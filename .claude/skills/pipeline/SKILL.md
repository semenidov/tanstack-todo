# Конвейер задач

Инструкции основной сессии. Общий процесс - `CONTRIBUTING.md` «Процесс фичи»; здесь только отличия конвейера. Большие новые фичи сюда не попадают - это обычный режим.

## 1. Сбор

`git fetch`; список открытых issue. Исключить:

- issue с открытым PR - это не новая задача; правки по такому PR идут в очередь отдельно (шаг 4);
- черновики (`[Draft]` в заголовке);
- эпики и зонтичные issue;
- большие новые фичи (>~12 критериев, несколько миграций, нужно обсуждение).

## 2. Анализ

Код читать с `origin/master`. По каждой issue:

- полнота спеки по «Формату спеки» - конкретные пробелы, не «спека неполная»;
- не устарела ли спека относительно кода (файлы, контракты, уже сделано);
- зависимости: общие файлы, порядок по смыслу;
- есть ли миграция.

Задача оказалась большой (>~12 критериев или миграция при занятом слоте) - «не для конвейера», предложить обычный режим.

## 3. План

Одно сообщение владельцу + push-уведомление:

- таблица «issue → готово / нужно дописать (вопросы) / не для конвейера»;
- порядок и зависимости.

Владелец отвечает на вопросы и одобряет набор. Задачи без вопросов стартуют сразу после одобрения, задачи с вопросами - после ответа; ответ вносится в тело issue до старта.

План и статус - в tracking-issue `pipeline: <дата>` с чеклистом задач; основная сессия обновляет его по ходу. Новая сессия продолжает конвейер с него.

## 4. Выполнение

- Один `implementer` за раз. Правки по открытым PR конвейера (вердикт verifier, фидбэк владельца) приоритетнее новых задач.
- Вердикт verifier основная сессия ждёт сама: фоновое ожидание прогона `verify.yml`, без опроса в цикле. Пока ждём - следующая задача.
- Ветка от свежего `origin/master`. Зависимая задача ждёт мержа предыдущей. Стек (base PR = ветка предыдущего PR) - только если иначе очередь стоит; base-ветку implementer получает от основной сессии.
- После мержа предыдущего PR - `git merge origin/master` в ветку стека (и в ветки с конфликтами), без force-push.
- Лимиты: не больше 3 непримёрженных PR конвейера; не больше одной непримёрженной миграции (общий `staging`, №57). Лимит достигнут - новые задачи не начинаем, ждём мержа.
- Запись ADR в ветке - с номером `??`. Номер ставит основная сессия, когда ветка догнала `master` (после мержа предыдущих PR); две ветки с `??` нумеруются в порядке мержа.
- Готовый PR (verifier «ок») - draft → ready и `[claude summary]` как в обычном режиме, но владельца не дёргаем по каждому - см. шаг 6.

## 5. Застрявшая задача

После 2 неудачных гипотез задача откладывается: комментарий в issue (что пробовали, где стоп), пометка в tracking-issue; конвейер идёт дальше. Владельца дёргаем, только если блокируется всё (например, все оставшиеся задачи зависят от отложенной).

## 6. Финал

Одна сводка владельцу + push-уведомление:

- PR, готовые к приёмке (у каждого есть `[claude summary]`);
- порядок мержа (зависимости, стек, миграция);
- отложенные задачи с причинами.

Tracking-issue обновить; закрывает его основная сессия, когда все PR конвейера смержены или закрыты.
